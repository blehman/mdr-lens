mdr-lens · Medical Data Review & Real-Time Visual Analytics views

One completed trial, replayed by data cut — plus a live public-registry view

A small set of views a Medical Data Review (clinical data review focused on patient safety) analyst or a Real-Time Visual Analytics / Risk-Based Quality Management (RBQM) lead might want: a completed public clinical trial replayed month by month as if its data cuts were arriving in real time, a live public-registry snapshot, liver safety screening, an adverse-event explorer with a one-patient timeline, site-level risk indicators, and data-quality checks.

§01 is a simulator: one completed public study, replayed by monthly data cut, never an ongoing trial. §02 fetches the public ClinicalTrials.gov registry fresh at build time. See Data, limits & what a real trial would add. No data here comes from any real patient or any employer's systems.

05 · then the sites

Site risk — key risk indicators (RBQM-style)

Risk-Based Quality Management (RBQM) watches a handful of key risk indicators (KRIs) per site instead of relying only on periodic visits. 17 sites here range from 1 subject to 51 — far too uneven for one fixed cutoff, so every limit below is a funnel-plot band that widens automatically for small sites. Read every flag next to its n; a flag on a 1-subject site is a prompt to look closer, not a verdict.

Methods, limits & what a real trial would add

What this is

A demonstration built on one public dataset: the long-standing CDISC (Clinical Data Interchange Standards Consortium) Pilot Project study, redistributed as SDTM tables by the pharmaverse community's pharmaverse/pharmaversesdtm package (Apache-2.0 license). It is a synthetic/anonymized teaching dataset used across the industry for exactly this kind of tooling, with nothing from any employer's systems. §01 (the live study simulator) replays that completed study by monthly data cut; §02 adds a live fetch of the public ClinicalTrials.gov registry. Everything else (fetch scripts, metrics, tests, and this page) rebuilds from public sources with one command, and the page runs offline — the only two things that ever reach the network are the pilot-data fetch and the registry fetch, both at build time, never while the page itself is open in a browser.

How the Live study simulator works (§01)

  • Monthly data cuts run from First Patient In (FPI, the earliest DM.RFSTDTC across all subjects) through the latest date seen in any domain, plus that exact end date as a final cut. Each cut filters every domain to only the records dated on or before it — exactly what a live extract would have shown that month. Every one of these cuts, from cut 1 (First Patient In) onward, is reachable one at a time with the stepper below.
  • The "current" cut shown by default advances one step per calendar day and loops over the cuts from the 25% enrollment milestone through the last cut, so a first-time visitor lands mid-study. Once the replay reaches its last cut, the next day's cut wraps back to the 25%-milestone cut and the cycle restarts on the date shown as "Cycle started" above. No commit or stored pointer marks this — it is recomputed from the clock every time the page is built.
  • "What changed" compares consecutive cuts: new adverse events, new lab results crossing ≥3× ULN (upper limit of normal), subjects newly meeting the potential Hy's Law pattern, and sites newly outside a funnel-plot limit (§05 method) — never re-litigating anything already shown at an earlier cut, since every domain only grows cut to cut.
  • Review-meeting cuts mark where cumulative enrollment first reaches 25/50/75/100% of its final total — a deterministic stand-in for cohort reviews or safety data review committee meetings, since this public dataset does not publish a real review calendar.
  • 52 of 306 subjects in this study are recorded as screen failures with no DM.RFSTDTC (they never reached a reference start date), and a further 26 AE / 225 LB records carry no parseable onset or collection date. Both groups have no date to be cut against, so they are correctly absent from every cut's enrolled/cumulative counts — while still counted in the whole-study totals in §04–06 and the hero stats above.

How the live registry view works (§02)

  • Query: lead sponsor (query.lead, which matches only the lead sponsor — not query.spons, which also matches collaborators) is "Hoffmann-La Roche" or "Genentech" (indexed on the registry as "Genentech, Inc."); filtered to Phase 1 or Phase 2, in status RECRUITING, ACTIVE_NOT_RECRUITING, NOT_YET_RECRUITING, or ENROLLING_BY_INVITATION.
  • The registry has no therapeutic-area field. Every study is bucketed by matching its derivedSection.conditionBrowseModule MeSH (Medical Subject Headings) ancestor/condition terms against this fixed, ordered list, first match wins: Neoplasms → Oncology; Immune System Diseases → Immunology; Infections → Infectious Disease; Nervous System Diseases → Neurology; Mental Disorders → Psychiatry; Eye Diseases → Ophthalmology; Cardiovascular Diseases → Cardiovascular; Respiratory Tract Diseases → Respiratory; Skin Diseases → Dermatology; Digestive System Diseases → Gastroenterology; Endocrine System Diseases / Nutritional and Metabolic Diseases → Metabolic / Endocrine; Musculoskeletal Diseases → Musculoskeletal; Hemic and Lymphatic Diseases → Hematology; Urogenital Diseases → Urogenital / Renal; Genetic Diseases, Inborn / Congenital, Hereditary, and Neonatal Diseases and Abnormalities → Genetic / Rare Disease; Wounds and Injuries → Injury / Wounds. A study whose terms match none of these is bucketed "Other (MeSH present)"; a study with no MeSH terms at all gets its own explicit "No MeSH category" bucket — neither is ever a guess at a category.
  • This view reflects only what sponsors have posted to the public registry, as of the fetch time shown — it makes no statement about, and is not, Roche's or Genentech's internal development pipeline.

What a real trial would add

  • A live Electronic Data Capture (EDC) / case report form (CRF) feed integrated directly into the dashboard, instead of a scheduled re-fetch of one public source replayed by date — §01–02 refresh on a schedule, but neither is a continuous live connection into a study's own EDC system.
  • The EX (drug exposure) domain for real dosing dates, instead of the DM reference start/end dates used here as a stand-in for exposure duration.
  • A published protocol visit schedule with real visit windows, instead of the ±7-day window around each visit's study-wide median day used here as a proxy.
  • A query workflow — the loop of raising a data query against a site, tracking it to resolution, and re-running these KRIs — which this page has no mechanism for.
  • Formal validation against a define.xml and the study's own CDISC conformance rules, not the hand-picked "required field" list used here.
  • Exact (not normal-approximation) funnel limits, multiplicity correction across many simultaneous KRIs, and clinical adjudication of every flag by a reviewer — what Gilead-Public/gsm and a real RBQM program do and this project does not.

Prior art (read, cited, not copied)

  • Gilead-Public/gsm (Good Statistical Monitoring, Apache-2.0) — the RBQM key-risk-indicator and funnel-plot method this project's site view follows.
  • pharmaverse/teal — Roche/Genentech's open-source clinical data exploration framework.
  • SafetyGraphics/safetyGraphics — the eDISH / Hy's Law graphic convention this project's liver-safety view follows.
  • ClinicalTrials.gov API v2 documentation — the public registry API §02 queries.

How to run it

uv run python scripts/fetch_data.py && uv run python scripts/fetch_registry.py && uv run python scripts/build.py && uv run pytest rebuilds every number on this page straight from the public pilot source and a fresh registry fetch, and re-runs every check, including independent recounts of the headline numbers direct from the raw tables (tests/test_independent_recount.py, tests/test_study_in_flight_recount.py). Then open web/index.html directly in a browser — no server needed, and no network calls happen while it's open. A scheduled GitHub Action (.github/workflows/refresh.yml) runs the same four commands daily and deploys the freshly built web/ directory to Pages without committing anything to the repository; if either fetch fails, the Action fails loudly and Pages keeps serving the previous deployment (see that workflow file's comments for the GitHub policy on scheduled workflows in a public repo, and how this one stays enabled).
